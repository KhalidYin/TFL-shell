# Skill 开发规则

> 历史说明：本目录保留为早期命名版本。当前正式复用 Skill 请以
> `.trae/skills/tfls-shell/` 下的 `TFLs-Shell SKILL` 为准。

## 1. 目标

本文件用于约束后续这个 Skill 的制定与开发方向，确保所有后续扩展都围绕
“可复用应用层 Skill 包”这一目标，而不是再次滑向“某个项目里的临时 workflow
实现”。

## 2. 核心定义

后续凡提到“这个 Skill”，默认指：

- 一个可复用的应用层 Skill 包
- 至少包含 `SKILL.md`
- 可以附带额外文档、样例、辅助脚本或映射资产

后续凡提到“项目实现”，默认指：

- 某个仓库中的支持性代码
- 生成器、推荐器、测试、命令行入口
- 为 Skill 服务，但不替代 Skill 包本身

## 3. 开发优先级

后续开发时，优先顺序应为：

1. 先定义 Skill 包的应用层目的、触发条件、边界和输出契约
2. 再决定是否需要补充包内文档、样例、映射表或脚本
3. 最后才决定某个具体项目如何实现这些要求

不要反过来从某个项目命令行或单文件实现倒推出 Skill 定义。

## 4. 允许加入的内容

为了提高调用可靠性，可以加入：

- 详细工作流说明
- 输入解释规则
- 输出字段说明
- 风险提示模板
- 术语映射规则
- 样例输入输出
- 辅助脚本
- 质量检查清单

## 5. 不应再发生的偏差

以下偏差应视为错误：

- 把 `skill.py`、CLI 子命令或单个脚本当成 Skill 包本体
- 把某个项目生成的 `output/` 文件当成 Skill 真值源
- 只写一份 `SKILL.md` 而不补必要的可靠性文档
- 先写实现，再补充应用层定义，导致定义被实现绑架

## 6. 变更要求

当 Skill 包发生实质变化时，至少应检查：

- `SKILL.md` 是否仍清楚描述触发条件与边界
- 包内补充文档是否仍与主入口一致
- 示例是否还能代表当前推荐工作流
- 如有辅助脚本，其输入输出是否仍与文档一致
- 如有项目实现依赖，项目说明是否明确把它标记为“实现层”

## 7. 建议的扩展方式

优先扩展以下类型内容：

- 更清晰的输入归一规则
- 更稳定的输出契约说明
- 更具体的风险与歧义处理
- 更可复用的样例与模板

谨慎扩展以下内容：

- 与某个仓库强耦合的命令行细节
- 过度依赖局部目录结构的说明
- 尚未稳定的实现策略

## 8. 审阅清单

每次审阅这个 Skill 时，至少检查：

- 这是应用层 Skill 包，还是又写回了项目实现说明
- 是否明确区分了 Skill 包、项目实现、业务输出
- 是否补充了足够的可靠性支撑材料
- 是否还有误导性历史口径残留

## 9. 维护口径

未来如继续扩展本 Skill，应遵循：

- package-first
- boundary-first
- reliability-first
- implementation-second
